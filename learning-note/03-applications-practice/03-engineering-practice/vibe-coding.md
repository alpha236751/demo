#  Vibe Coding：感觉驱动的编程新范式
Vibe Coding 是 AI 大牛 Andrej Karpathy（前OpenAI/Tesla AI主管）在2025年初提出的概念。他的原话是：
> "完全沉浸在氛围中，拥抱指数级增长，忘记代码的存在。"

翻译成大白话就是：**不要纠结代码的每一个细节，跟着感觉走，让AI帮你实现想法。**

## Vibe Coding 的核心原则
1. **意图优先**：先描述你想要什么效果，而不是告诉AI怎么写代码
2. **快速迭代**：不追求一次完美，拥抱「生成 → 测试 → 修正」的循环
3. **信任但验证**：相信AI的能力，但始终检查关键逻辑
4. **上下文经营**：持续维护和优化提供给AI的背景信息

## Vibe Coding 适用场景
- 原型开发、概念验证（快速把想法变成可运行的东西）
- 个人项目、学习项目（试错成本低）
- 探索性编程（不确定最终效果，边做边看）
- UI/前端开发（可视化反馈快，容易判断好不好）

## Vibe Coding 需谨慎的场景
- 生产环境的核心系统（银行、医疗等）
- 安全敏感代码（认证、加密等）
- 性能极致要求的场景

> 提示：Vibe Coding 不等于"乱来"。它的精髓在于改变你的关注点 —— 从关注"代码怎么写"转向关注"产品好不好用"。

#  Agentic Engineering：工程化升级范式
系统性地编排和协调多个AI智能体（AI Agent）协同工作

## 为什么纯 Vibe Coding 在大项目中不够用
Vibe Coding 对于做小项目、快速原型非常好用，但当项目变大变复杂时，纯粹的"跟着感觉走"会遇到麻烦：
- 代码质量不可控：AI可能写出能跑但很乱的代码，积累成"技术债务"
- 前后矛盾：AI在不同对话中可能给出相互冲突的实现方式
- 缺乏全局视角：AI可能只关注当前的小任务，忽略对整体架构的影响
- 难以协作：没有统一规范时，多个人（或多次会话）的代码风格各异

这就像建房子 —— 自己搭一个小木屋可以随意发挥 (Vibe Coding)，但要建一栋大楼就必须有图纸、有规范、有质检 (Agentic Engineering)。

## 智能体协作模式
- 领导者-执行者模式(leader-worker)
- 管道式协作(pipeline)
- 对等协作(peer-to-peer)

## 自主决策和任务分解
优秀AI编程智能体遵循先思考后执行的工作模式。

### Plan-Act-Observe-Reflect 循环
1. **Plan（规划）**：梳理完成目标所需全部步骤
2. **Act（行动）**：执行单步开发操作
3. **Observe（观察）**：校验执行结果，发现问题
4. **Reflect（反思）**：针对问题制定修正方案
5. 循环回到 Plan，推进后续任务

### 任务分解原则 —— MECE
MECE（Mutually Exclusive, Collectively Exhaustive）释义：**相互独立，完全穷尽**。

示例：拆分「构建一个博客系统」
- 1. 用户系统（注册、登录、个人资料）
- 2. 文章系统（创建、编辑、删除、列表）
- 3. 评论系统（发表、删除、回复）
- 4. 分类标签（创建分类、打标签、按分类筛选）
- 5. 部署上线（打包、配置服务器、域名）
特点：子任务无重叠，合并后覆盖全部业务需求。

> 提示：使用 Claude Code 最佳实践：先让AI输出完整规划，人工确认后再执行代码生成，大幅减少返工。

# 规范驱动开发 SDD（Specification-Driven Development）
## 为什么AI编程需要"规范"
模糊描述会造成信息偏差，对应AI编程领域即“垃圾进，垃圾出”，宽泛需求会产出不符合预期的成果。

规范（Specification）是人与AI之间的开发“合同”，明确三类核心信息：
- 要做什么：功能需求
- 怎么做：技术方案
- 做到什么程度：质量标准

完整规范可消除信息歧义，让AI精准对齐开发意图。

## 需求规范：PRD文档
PRD（Product Requirements Document，产品需求文档），核心用于描述**要做什么**。

### 标准书写格式
#### 用户故事（User Story）通用模板
```
作为一个 [角色]，
我希望 [功能]，
以便 [价值/目的]。
```
示例：
```
作为一个博客读者，
我希望能按标签筛选文章，
以便快速找到我感兴趣的内容。
```

#### 验收标准（Acceptance Criteria）Given-When-Then 模板
```
Given（前提条件）：系统预设状态
When（操作）：用户执行的行为
Then（预期结果）：操作后系统应呈现的效果
```
示例：
```
Given（前提条件）：系统中有20篇文章，其中5篇标记了"Python"标签
when（操作）：用户点击"Python"标签
Then（预期结果）：页面只显示这5篇标记了"Python"标签的文章
```

### AI辅助生成PRD通用Prompt模板
```
我想做一个个人书签管理工具。

请帮我生成一份完整的PRD文档，包含：
1. 项目概述（一句话描述）
2. 目标用户
3. 核心功能列表（按优先级排列：Must Have / Should Have / Nice to Have）
4. 每个功能的用户故事和验收标准
5. 非功能需求（性能、安全、兼容性）

请用Markdown格式输出。
```

## 技术规范：SPEC文档
SPEC（Technical Specification，技术规范文档）用于定义**怎么做**。

### 完整SPEC文档组成：
| 模块 | 内容 | 说明 |
| ---- | ---- | ---- |
| 系统架构 | 整体架构设计图 | 定义前后端交互逻辑 |
| 技术选型 | 项目所用技术、框架 | 示例：Next.js + Prisma + SQLite |
| 数据模型 | 数据库表结构设计 | 包含数据表清单、各表字段定义 |
| API接口 | 接口完整定义 | 每个接口的URL、请求参数、返回数据格式 |
| 目录结构 | 项目文件组织规范 | 规定各类代码存放文件夹 |

### 由PRD生成SPEC的Prompt模板
```
基于以下PRD文档，请生成对应的技术规范文档（SPEC）：
[粘贴你的PRD内容]

要求：
1. 推荐技术选型并说明理由
2. 设计完整的数据模型（包含字段类型和关系）
3. 列出所有API接口（RESTful风格）
4. 给出建议的项目目录结构
```

### 质量规范
质量规范定义项目**合格标准**，分为三类：
1. **编码规范**：统一代码风格、命名规则、注释标准
2. **测试规范**：明确需覆盖的全部测试场景
3. **安全规范**：包含输入校验、身份认证授权、数据安全保护

> 初学者无需一次性编写完整规范，可从简易PRD起步，随项目迭代完善；规范核心作用是消除人与AI之间的沟通歧义。

### 规范文件的组织与管理
目录规范
推荐在项目根目录新建 `specs/` 文件夹统一存放所有规范文档，完整目录结构如下：
```
my-project/
├── specs/
│   ├── PRD.md          # 产品需求文档
│   ├── SPEC.md         # 技术规范文档
│   ├── ARCHITECTURE.md # 架构设计文档
│   └── API.md          # API 接口文档
├── src/                # 项目源代码
├── CLAUDE.md           # 给 Claude Code 的项目全局说明
└── package.json        # 项目配置文件
```

核心价值
规范文档可直接作为AI编程工具的上下文输入；将 `SPEC.md` 提供给 Claude Code 后，AI 能够严格依照预设技术方案生成对应代码。

## 模型选型
### 选型决策树
编程任务模型选择流程：
1. 简单任务（代码补全、格式化、小修改）
- 追求最快速度：Claude Haiku / GLM-4.5-Air / 本地 Qwen
- 追求最低成本：DeepSeek API / 本地 Ollama
- 完全免费：本地 Ollama 模型

2. 日常开发（功能实现、Bug修复、代码生成）
- 英文项目：Claude Sonnet（首选）
- 中文项目：Claude Sonnet 或 通义千问 / GLM-4.7
- 预算紧张：DeepSeek V4 / GLM / Kimi

3. 复杂任务（架构设计、算法难题、疑难Bug）
- 深度推理：Claude Opus / GPT-5.5 / DeepSeek V4 Pro
- 超长代码库：Gemini Pro（支持1M上下文）

4. 特殊场景
- 离线/隐私要求：本地 Ollama + Llama/Qwen
- 截图转代码：GPT-5.5 / GPT-4o 系列（多模态能力）
- 国内直连要求：DeepSeek / 千问 / GLM

### 成本优化策略
1. 策略一：分层使用
按任务复杂度匹配对应价位模型，避免高算力浪费：
- 简单任务 → Haiku / GLM-4.5-Air / 本地 Qwen（低成本 $）
- 日常任务 → Sonnet / DeepSeek V4 Pro（中等成本 $$）
- 复杂任务 → Opus / GLM-5.1（高成本 $$$$）
类比：无需每次出行都打专车，按需选择更划算。

2. 策略二：Prompt Cache（缓存复用）
Claude、GPT 均支持该能力；
若每次请求携带大量重复固定上下文（如 CLAUDE.md、规范文档），后续会话可复用缓存内容，大幅减少重复文本计费。

3. 策略三：本地模型补充
代码格式化、注释生成等轻量化任务，使用 Ollama 本地部署模型处理，零API调用费用。
